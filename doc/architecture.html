02 / Critical flows

三条关键数据流

控制面只负责生成可信的运行时快照；执行面消费快照，不直接读取或拼装管理表单中的原始配置。

FLOW A / CONTROL

创建或更新 Agent

配置变更即时生效，但不影响绑定旧 revision 的在途任务。

  1. 管理员通过独立认证进入 /admin。
  2. 提交 slug、执行器、Schema、并发和密钥引用。
  3. 服务端严格校验并在事务中写入新 revision。
  4. 构建不可变 AgentRuntime，原子替换 Registry。
FLOW B / PUSH

执行 Agent 请求

同一动态路由承载全部 Agent，每个 slug 使用自己的策略。

  1. POST /agent/server1 到达 Agent Gateway。
  2. 按 slug 读取 runtime，并执行签名与输入 Schema 校验。
  3. 幂等登记后进入有界队列，执行全局和 Agent 限流。
  4. Claude Code 或 Rust Agent 产出结果并完成契约校验。
FLOW C / ASYNC

Pull 与可靠回传

后台任务由 Supervisor 管理，结果通过持久 Outbox 交付。

  1. Registry 变更触发对应 Pull Worker 启停或滚动重建。
  2. Worker claim 任务并在执行期间 renew 租约。
  3. 执行结果与回调事件在本地事务中持久化。
  4. Outbox 按退避策略重试 callback / complete。

04 / Architecture boundaries

关键设计原则

Claude Code 属于本机高权限执行边界，因此容量、安全、取消和审计必须在第一版就成为架构组成，而不是后续补丁。

P-01

静态启动配置与动态 Agent 配置分离

管理密码哈希、DATABASE_URL 和主密钥属于环境变量；Agent 业务配置由管理端写入 PostgreSQL 并保留 revision。

P-02

禁止 shell 字符串拼接

Claude Code 使用 tokio::process::Command 参数数组，限制 executable、cwd、env、运行时长和输出大小。

P-03

双层容量保护

全局并发限制保护主机，每 Agent Semaphore 保证租户隔离；队列必须有界，过载明确返回 429 或 503。

P-04

可靠状态而非内存承诺

幂等键以 (agent_id, key) 隔离，并记录请求 hash；异步回调通过持久 Outbox 重试，进程重启不丢失。
